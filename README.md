# rate-wave

A simple web app for listening to and rating music recordings on a five-star scale — with BPM tapping and waveform visualizations, straight in the browser.

**Fully static PWA · zero backend**

</div>

---

## Why rate-wave?

Most players lock your ratings inside their own library database. rate-wave does the opposite: your ratings live **in the files themselves**. And because it's a static web app, there is nothing to install and nothing to run — just open it.

- **Rate with 5 stars** — ratings are written into the MP3 files as ID3 tags, so they stay with your music wherever the files go.
- **Tap the tempo** — tap-out a track's BPM with a button; it gets saved into the file as a tag too.
- **Waveform per track** — clickable waveform for quick scrubbing and previewing.
- **Your files, your place** — use a pCloud account or a local folder as the music source.
- **Works everywhere** — responsive PWA you can install on desktop and Android.

## How it works

1. **Connect a source** — sign in to pCloud (OAuth) or pick a local folder; the library listing is cached so it loads instantly next time.
2. **Browse and play** — filter by year folder, search by filename, sort by name, rating, tempo, or last played.
3. **Rate and tag** — a rating or BPM change patches the MP3's ID3 tag and uploads the file back to its source. Changes made offline are queued and flushed when you're back online.
4. **Resume anywhere** — the app remembers your session, restoring the last track and playback position on every visit.

Ratings use the `POPM` tag in the Windows Media Player convention, so any compatible player (WMP, foobar2000, MusicBee, Mp3tag, Poweramp…) reads and writes the same stars. Nothing is deleted from your files — only the rating-related tag is touched.

> [!NOTE]
> The app runs entirely in your browser (Chrome desktop / Android). Opening it from a `file://` URL is not supported — use the dev server or the hosted build.

## Getting started

Prerequisites: **Node.js 20+** and npm.

```bash
git clone https://github.com/danielmroczek/rate-wave.git
cd rate-wave
npm install
npm run dev
```

Open `http://localhost:5173/` and connect a music source.

```
    auth-flow.js       — initAuth, handleOAuthReturn (network-aware error handling)

    oauth-page.js      — Vite page entry for oauth.html (prod OAuth redirect)
    pcloud-api.js      — pCloud API calls (network vs auth error tagging)
    token-store.js     — token persistence: localStorage + IDB mirror (spec §4)
    auth.test.js       — unit tests for auth flows
  store/db.js          — IndexedDB `rate-wave` v1: 6 stores + full data reset
  store/db.test.js     — schema & reset tests
vite.config.js         — base /rate-wave/, MPA (index + oauth), SW precache plugin
worker/
  src/worker.js        — READ-PROXY (Cloudflare Worker): /getfilelink passthrough
                         + /stream bajtów z ACAO; rate-limit ≤12 zaległych getfilelink;
  test/worker-test.js  — unit testy workera (node:test, `node test/worker-test.js`)
  wrangler.jsonc       — config workera (workers.dev, ALLOWED_ORIGINS)
```

The whole data layer is **IndexedDB** (`rate-wave` v1): settings, sources, library listing, track metadata (rating, gain, waveform peaks, last-played), an offline rating queue, and the current session. "Clear all data" is a single button away — it deletes the database and `localStorage`; your files on pCloud are never touched.

## Stack

**Vite+** ([viteplus.dev](https://viteplus.dev)) — one unified toolchain: Vite (v8, Rolldown), Vitest, oxlint and oxfmt in a single `vite-plus` devDependency. Vanilla-JS ES modules, no framework.

Deployment is a plain static build on **GitHub Pages** ([`.github/workflows/deploy.yml`](.github/workflows/deploy.yml)); file downloads go through a small **READ-PROXY** (Cloudflare Worker) that also serves byte ranges. For the full picture see the [specification](docs/spec.md) and the [glossary](docs/CONTEXT.md).

### READ-PROXY worker

`fetch()` reads of track bytes (ID3 tag reads, waveform, ReplayGain, rating rewrite) go through the READ-PROXY Cloudflare Worker ([`worker/`](worker/)) — pCloud file hosts never return `Access-Control-Allow-Origin`, so browsers can't fetch those bytes directly. Playback via `<audio>` stays direct (uses the link from `getfilelink`).

Endpoints (auth is a passthrough of the user's own OAuth token; see [ADR 0001](docs/adr/0001-read-proxy-auth.md)):

| Endpoint                                   | What it does                                                                                                                        |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| `GET /getfilelink?fileid=…&access_token=…` | calls pCloud `getfilelink`, returns the file link + `expires` (worker is stateless, holds no secrets)                               |
| `GET /stream?url=…`                        | fetches bytes from the pCloud file host and streams them with `Access-Control-Allow-Origin`; forwards `Range` (206 Partial Content) |
| `GET /stream?fileid=…&access_token=…`      | same, but generates the link in the same invocation (retry loop over fresh links × all `hosts[]`) — preferred for JS byte reads     |
| `POST /head?access_token=…` — body `{"fileids":[…]}` | batch ID3 head prefetch: up to **20 fileids**, fetches the first 8 KB of each (`Range: bytes=0-8191`) with per-file IP-binding retry, 12 concurrent fetches; streams **NDJSON** (`application/x-ndjson`) line per file as soon as it's ready: `{"fileid":123,"status":"ok","bytesBase64":"…"}` or `{"fileid":123,"status":"error","code":"…"}` |
| `GET /health`                              | smoke check                                                                                                                         |

Guards: allowed-origin list (`ALLOWED_ORIGINS` in `wrangler.jsonc`), target host limited to `*.pcloud.com` (no token in file URLs), in-memory limit of 12 outstanding `getfilelink` calls per token → `429`. Batch size on `/head` is capped at 20 (2 subrequests per file ≈ 40, within the 50-subrequests-per-invocation free-plan limit). Tokens are never logged.

Local development: `cd worker && npm install && npm run dev` (wrangler, `http://localhost:8787`); point the app at it with `VITE_RW_PROXY_URL`. Deployment runs on pushes to `main` touching `worker/**` ([`deploy-worker.yml`](.github/workflows/deploy-worker.yml)) and needs the `CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID` repo secrets.

> [!NOTE]
> pCloud file links are **IP-bound** (undocumented: a link returns HTTP 410 "generated for another IP address" when fetched from a different IP). For JS byte reads use the `/stream?fileid=…` mode — it regenerates the link and retries across all `hosts[]` in one invocation (~85% per-request success; failures surface as `pcloud_link_unavailable`). Details in [the probe research](docs/research/probe-origin-read-proxy.md).

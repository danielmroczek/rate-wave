# Wydajność ~3000 pozycji: wirtualizacja i lazy odczyt tagów — research

Data: 2026-10-27 · Źródła: docs.pcloud.com (`listfolder`), MDN (Web Workers, Web APIs w workerach), GitHub (Clusterize.js, TanStack Virtual, music-metadata), **własne pomiary empiryczne na produkcji pCloud** (ten sam dostęp, co testy T1–T5 biletu 11).

Ticket: `.scratch/music-rater-target/issues/16-performance-3000.md`

---

## Podsumowanie (werdykt)

Biblioteka = 3635 MP3 w 16 podfolderach rocznikowych + podfoldery tag-test/warped/zoom; 5,8 GiB (typowy plik ~0,3–3 MiB). Listing całości to **jeden** rekurencyjny `listfolder`: **433 ms / 2,53 MiB JSON** (desktop; na mobile ~2–5 s, rozmiar ten sam). Lista: **manualny windowing vanilla-JS** (okno ~30 rzędów + spacers), bez biblioteki. Lazy tagi: masowy odczyt 3635 plików na starcie sesji jest **niewykonalny i zbędny** — `getfilelink` kosztuje ~93 ms i pozostaje sekwencyjnym wąskim gardłem API (ryzyko rate-limitu przy masowym równolegleniu); pełny crawl to ~19 min przy 1-równoległości i nadal ≥ ~6 min przy najlepszym rozdzieleniu pracy. **Strategia: cache IndexedDB jest źródłem ocen na starcie; tagi czytane lazy per-ekran w workerze; pierwsze uruchomienie = stopniowe dochodzenie pozycji, nie spinner-cały-ekran.**

Wzorzec listy = manualny windowing bez biblioteki; onboarding = stopniowe dochodzenie (krótki spinner 1–2 s na listing → lista z metadanych listfolder → natychmiastowe oceny z IndexedDB → lazy ratingi per-screen w kolejce workerów); stronicowanie pCloud = **nie istnieje** (parametr `limit` ignorowany, potwierdzone empirycznie) — przyjmujemy 1× recursive `listfolder` + cache w IDB.

## 1. Wirtualizacja listy bez frameworka — wzorce, koszty

### Wzorce

**a) Manualny windowing**

Kontener scrollowalny ze spacerem wewnętrznym o wysokości `n_items × row_height` (stała wysokość rzędu); scroll listener (throttling przez `requestAnimationFrame`, `passive: true`) wylicza widoczny zakres indeksów `[start..end]` (z nadmiarem ~10 pozycji na szybki scroll) i renderuje tylko ten fragment, pozycjonowany `transform: translateY(start × row_height)`. Przy 3635 pozycjach i stałej wysokości rzędu (56–72 px) to ~30–50 linii kodu. Kluczowa zaleta: pełna kontrola nad sortowaniem/filtrowaniem — kolejność w tablicy w pamięci jest kolejnością renderowania.

**b) Biblioteki**

- [Clusterize.js](https://github.com/NeXTs/Clusterize.js) — vanilla-JS, ~10 kB min (~3,5 kB gzip); 7,3k gwiazdek, **ostatni commit 3 lata temu** (2023), MIT. Prosty model „tablica danych → rzędy", stałe wysokości. Ryzyko: martwy projekt.
- [@tanstack/virtual-core](https://tanstack.com/virtual/latest) (TanStack Virtual) — headless, framework-agnostic; sam rdzeń ~2–3 kB gzip. Wyróżnik: dynamiczne wysokości i pomiary. Overkill przy liście o stałych wysokościach.
- Wspólny wzorzec wszystkich zewnętrznych bibliotek = dokładnie ten windowing co w (a); przy stałych wysokościach nie wnoszą nic ponad wygodę.

**Rekomendacja: manualny windowing w vanilla-JS.** Uzasadnienia:

1. Stałe wysokości rzędów (pozycja = nazwa pliku + rocznik + gwiazdki 1–5) — dynamiczne wysokości, główny argument za TanStack, nie występują.
2. Sortowanie/filtrowanie = operacja na tablicy w pamięci (`Array.prototype.sort` / `filter`), potem re-render okna. Zachowanie „przy sortowaniu zostań na zaznaczonym elemencie" = `scrollTo({ top: newIndex × row_height })` po przeliczeniu indeksu. Zero konfliktu z windowingiem.
3. Mobile Chrome: 60 FPS dają rAF-throttled scroll handler + passive listener + `content-visibility: auto` na rzędach; przy oknie 25–50 rzędów manipulacja DOM < 5 ms na klatkę.
4. DOM footprint: tylko widoczne okno ma węzły (< ~50 rzędów × ~12 węzłów = < 600 węzłów). Wariant „bez wirtualizacji" (render wszystkich 3635) to ~44 000 węzłów DOM — na średnich telefonach jank przy scrollu jest realny (obserwowany już przy > 5 tys. węzłów). Wirtualizacja jest **konieczna**, nie opcjonalna.

### Koszty na mobile

- Budżet ramki 60 FPS = 16,7 ms. Windowing z 30 rzędami: < 2–3 ms JS + 3–5 ms paint na typowym średnim Androidzie — pełny zapas.
- Pamięć: 3635 × ~200–400 B na obiekt = **~1–1,5 MiB heap** na samą tablicę; string JSON 2,53 MiB + sparsowane obiekty chwilowo ~5–8 MiB — pomijalne.
- Scroll momentum na Android Chrome działa natywnie; wystarczy brak ciężkiej pracy w handlerze scrolla.

## 2. Lazy odczyt tagów — parsowanie `music-metadata` w Web Workerze

### Pomiary empiryczne z pCloud (2026-10-27)

| pomiar | wartość |
| --- | --- |
| `listfolder` recursive (całe drzewo rec) | **433 ms**, odpowiedź **2,53 MiB** |
| `listfolder` per-roczników (19 folderów, sekwencyjnie) | **razem 2162 ms** |
| `getfilelink` (API, 1 plik) | **92,8 ms/request** (stabilnie 89–93 ms) |
| Range 0–65535 (64 KB, serwer content) | **169–200 ms/request** |
| razem 1 plik (getfilelink + 64 KB) | **~318 ms/plik** sekwencyjnie |
| 3 równoległe łańcuchy × 7 plików (21 plików) | **125,3 ms/plik** efektywnie (2,5×) |

Rozbicie opóźnienia 64 KB (curl timing): dns=5 ms, conn=45 ms, **tls=93 ms**, ttfb=131 ms, total=169 ms (połączenie keep-alive po rozgrzewce). Serwer contentu: `HTTP/1.1 206 Partial Content`, `Server: CacheHTTPd v1.0`, `Accept-Ranges: bytes`, `Keep-Alive: timeout=30` — **brak HTTP/2** (potwierdzone nagłówkami). To znaczy, że limit równoległości przeglądarki na ten host = klasyczne ~6 połączeń HTTP/1.1.

### Wyliczenie masowego odczytu 3635 plików

Koszt per plik = `getfilelink` (≈93 ms) + Range 64 KB (≈169–200 ms).

- **1-równoległość: 3635 × 0,318 s ≈ 1155 s ≈ 19,2 min.** Niedopuszczalne na starcie.
- **6-równoległość** (limit HTTP/1.1 na host contentów): transfer spada ~6×, ale `getfilelink` to osobne requesty do `eapi.pcloud.com` — 3635 wywołań API w ~2 min niesie **ryzyko rate-limitu**; nie da się tego obejść inaczej niż kolejkowaniem.
- **Rozdzielenie przepływów** (kolejka `getfilelink` + pool fetch na content): realne minimum sesji ≈ **6 min** (93 ms × 3635 ≈ 340 s wyłącznie na API — nieprzyspieszalne), odczyty transferowe ~2 min przy 6 połączeniach.
- **Wicej niż ~10-równoległość bez sensu**: wąskim gardłem staje się API `getfilelink`, a agresywne 32 równoległe fetchy grożą 429.

**Wniosek: masowy crawl wszystkich tagów na starcie sesji nie ma sensu** (6–19 min opóźnienia) **i nie jest potrzebny**, bo:

1. **Cache IndexedDB po kluczu `'pcloud|'+fileid`** (bilet „Model stanu i trwałości") jest trwały: po pierwszym (stopniowym) crawlu aplikacja startuje z pełną wiedzą o ocenach bez sieci. **Brak ramki POPM też cache'ujemy** (`rating: null`), żeby nie crawlować plików bez oceny przy każdym starcie. Unieważnienie per-rekord: size+modified.
2. **Per-screen lazy**: użytkownik widzi ~20 rzędów; paczka ekranowa 20 plików × 318 ms / 6 połączeń ≈ **~1 s na ekran** w najgorszym przypadku (cold), szybciej z cache'owanymi linkami.
3. **Istniejące oceny (157 z WMP wg audytu biletu 10) pojawiają się od razu z IDB** — zgodne z biletem 10: brak ramki = brak oceny; 157 ocen od pierwszego uruchomienia bez migracji.

### Strategia pierwszego ładowania (spinner vs stopniowe dochodzenie)

Kolejność (zgodna z biletem 07):

1. **Start**: walidacja tokena (`userinfo`) + sprawdzenie cache listingu w IDB (`library`) — jeżeli jest, **0 requestów sieciowych na listing**, start błyskawiczny.
2. **Brak/zmiana cache**: 1× `listfolder(recursive)` — desktop 433 ms, mobile ~2–5 s. W tym czasie lista szkieletowa (skeleton) + krótki wskaźnik; UI nie jest blokowane.
3. **Odczyt ocen z IDB `tracks`** po kluczu `'pcloud|'+fileid` — instant (batchowo 3635 rekordów, ~10–50 ms).
4. **W tle**: kolejka workerów (1–2); pliki widoczne na ekranie (IntersectionObserver) → fetch 64 KB Range → `music-metadata.parseBlob` w workerze → walidacja POPM → persist do IDB → re-render rzędu. **Efekt „stopniowego dochodzenia pozycji"** — gwiazdki dopisują się na żywo.
5. **Sortowanie/filtrowanie po ocenie działa zawsze** — na wartościach z cache; status „brak danych" (nie-crawlowane) rozróżniamy od „brak oceny" (ważne dla biletu 17).

### `music-metadata` w workerze — uwagi praktyczne

- API przeglądarkowe: `parseBlob()`, `parseWebStream()`, `parseBuffer()`, `parseFromTokenizer()` — cross-platform, [README](https://github.com/Borewit/music-metadata) (sekcja „Cross-platform functions").
- **Web Worker ma `fetch()`, `XMLHttpRequest` i `IndexedDB`** — [MDN: functions available to workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Functions_and_classes_available_to_workers). Cały pipeline (fetch Range → parse → zapis IDB) może działać **w całości w workerze**; do UI wraca tylko wynik ratingu.
- **Parsowanie w obrębie workera sekwencyjnie** — [FAQ music-metadata](https://github.com/Borewit/music-metadata) odradza masowe równoległe `parseBlob`; równoległość robimy liczbą workerów (1–2), nie w środku workera.
- **Opcje**: `duration: false` (default — inaczej parser może czytać cały plik dla czasu); `skipCovers: true` — pomija okładki, reduceruje pamięć i ryzyko potrzeby większego Range.
- **Rozmiar Range: 64 KB** — test na pliku z oceną (fileid 71496730995, zakresy 16/32/64/128 KB): **POPM obecny już w 16 KB**; 64 KB = bezpieczny margines na większe nagłówki ID3v2.3 (RVA2/TXXX itd.). Koszt dodatkowych 48 KB przy TTFB ~131 ms: ~30–60 ms — marginalny.
- **Cache linku `getfilelink` w IDB** — linki ważne ~6 h (`expires` potwierdzony empirycznie: 18:19 → 00:19); cache eliminuje duplikaty wywołań w obrębie sesji.

### Opcja streamingowa (na przyszłość)

[streaming-http-token-reader](https://github.com/Borewit/streaming-http-token-reader) (ekosystem `music-metadata`) — tokenizer czytający metadane przez HTTP range requests; może zastąpić ręczny fetch 64 KB. Nie wymagane dla MVP.

## 3. Stronicowanie `listfolder` pCloud — koszt listowania

### Brak stronicowania — potwierdzone empirycznie

[Dokumentacja listfolder](https://docs.pcloud.com/methods/folder/listfolder.html) **nie ma parametrów paginacji** (limit „1000 na call" znany z innych endpointów pCloud). Test empiryczny:

```
listfolder?folderid=<2019-2>&limit=10   # folder ma 322 wpisy
→ 322 wpisy w odpowiedzi; limit ZIGNOROWANY
```

Brak `pagestart`/`pagelimit`, brak wskazówek „następna strona" w odpowiedzi. **Paginacji nie ma — trzeba przyjąć jeden recursive call albo kilka per-folderów.**

### Koszty: 1 recursive vs per-roczniki (empirycznie)

| strategia | requesty | czas (desktop) | rozmiar |
| --- | --- | --- | --- |
| 1× `recursive=1` na `/audio/rec` | **1** | **433 ms** | **2,53 MiB** |
| 19× `listfolder` per-roczników (sekwencyjnie) | 19 | **2162 ms** | ~2,5 MiB łącznie |

Na mobile (RTT ~100–300 ms): recursive = 1 RTT + 2,53 MiB transferu (~2–5 s na 4G) vs per-roczniki sekwencyjnie = 19 × (RTT + transfer) ≈ 4–10 s; równoległość 19 callów zredukowałaby to do ~1–2 s, ale to 19 requestów vs 1 — bez zysku. Dodatkowo recursive daje **spójność w jednym momencie czasowym** (jedna odpowiedź zamiast 19 różnych chwil).

**Rekomendacja: 1× recursive `listfolder` na korzeń biblioteki; cache w IDB (bilet 07) → 0 requestów przy następnych startach.**

### Limity i filtrowanie

- `limit` — ignorowany. `nofiles=1` — tylko struktura podfolderów (nie używamy; potrzebujemy `size`+`modified` per plik).
- Filtrowania server-side brak: 450 plików spoza MP3 (`.alc`, `.als`, `.cfg`, `.ico`, `.wav`, `Desktop.ini`) i 798 plików `.asd` (Rekordbox) odfiltrowujemy client-side po `contenttype === 'audio/mpeg'` / `category === 3` + nazwa `.mp3`.

## 4. Gdzie realnie leży wąskie gardło

| operacja | koszt | kiedy |
| --- | --- | --- |
| Sort 3600 rekordów (`Array.sort`) | **1–5 ms** (desktop V8), ~5–15 ms (mobile) | każde sortowanie/filtr |
| Render widocznego okna (~30 wierszy) | **3–6 ms** | każdy re-render |
| `listfolder` recursive (cała biblioteka) | **433 ms** (desktop) / ~2–5 s (mobile) | 1× na świeży cache; 0 z IDB |
| Odczyt ratingów z IndexedDB (3635 rekordów) | **~10–50 ms** (batch getAll) | 1× na starcie |
| `getfilelink` + 64 KB Range per plik | **~318 ms** sekwencyjnie; ~125 ms przy 3× równoległości | lazy per-screen; 0 z IDB |
| Pełny crawl 3635 plików (getfilelink sekwencyjne) | **≥ ~6 min** | **nie wykonujemy** |

**Sort 3600 rekordów: rzędu jednostek milisekund** — V8 Timsort na 3600 obiektach z prostym kluczem (number/string) to ~1–3 ms; z niestandardowym comparator ~3–5 ms; na słabym mobile ~5–15 ms — nadal w budżecie ramki + debounce przy searchu. **Sortowanie w Web Workerze zbędne** (overhead postMessage > czas sortowania).

**Render:** okno 20–30 rzędów = 3–6 ms — nie wąskie gardło.

**Wąskie gardło = I/O sieciowe + koszt API `getfilelink`** (93 ms × 3635 ≈ 340 s nieprzyspieszalnego minimum). Stąd wniosek nadrzędny: **cache IndexedDB jest kluczem wydajności tej aplikacji**; odczyty sieciowe tylko lazy per-screen przy pierwszym uruchomieniu, potem zero dzięki IDB.

## 5. Werdykt: decyzje

1. **Wzorzec listy: manualny windowing vanilla-JS** — stała wysokość rzędu, ~30 rzędów visible (+10 nadmiaru), spacer, rAF-throttled passive scroll, pozycjonowanie `transform: translateY`. Zero zależności. Sortowanie/filtrowanie = tablica w pamięci + re-render + `scrollTo` po nowym indeksie zaznaczonego elementu. Fallback przy dynamicznych wysokościach: [@tanstack/virtual-core](https://www.npmjs.com/package/@tanstack/virtual-core). **Nie rekomenduję Clusterize.js** (brak rozwoju od 2023).

2. **Strategia pierwszego ładowania (mobile): stopniowe dochodzenie, nie spinner.** Kolejność T0–T3 jak w §2: listing (lub 0 z cache) → lista z ocenami z IDB → lazy crawl widokowych pozycji w workerach → gwiazdki dochodzą na żywo; interakcja nieblokowana przez cały czas.

3. **Stronicowanie pCloud: nie istnieje** — `listfolder` nie ma paginacji (limit ignorowany, potwierdzone empirycznie). Decyzja: **1 recursive call na całą bibliotekę** (433 ms / 2,53 MiB) + cache IDB z unieważnieniem per size+modified. Per-roczniki bez empirycznej przewagi — odpadają.

4. **Wąskie gardło: I/O i `getfilelink`**, nie sort ani render. Rozmiar Range = **64 KB** (16 KB wystarcza na POPM, 64 KB = margines na większe nagłówki; koszt marginalny).

## Testy empiryczne — komendy (PowerShell + curl; 2026-10-27)

```powershell
# T1: recursive całego drzewa rec — czas i rozmiar
curl.exe -s -o tmp.json "https://eapi.pcloud.com/listfolder?access_token=$tok&folderid=18334037058&recursive=1&timeformat=timestamp"
# wynik: 433 ms, 2,53 MiB (2 649 266 znaków; 4883 files, 75 dirs; mp3=3635, asd=798, inne=450)

# T2: per-roczniki (hi-q-recordings folderid 18335400545 — 19 subfolderów)
# sekwencyjnie: suma 2162 ms (90–113 ms/req; outlier 2024-02=339 ms)

# T3: limit ignorowany — folder 2019-2 ma 322 wpisy
curl.exe "https://eapi.pcloud.com/listfolder?access_token=$tok&folderid=18335796537&limit=10"
# → 322 wpisy = BRAK paginacji

# T4: getfilelink + Range 64 KB — 21 plików z 2019-2:
# SEQ (1 połączenie): 6679 ms => 318 ms/plik
# PAR (3 równoległe łańcuchy po 7): 2631 ms => 125,3 ms/plik (2,5×)

# T5: składowe opóźnienia 64 KB (curl -w):
# dns=5ms conn=45ms tls=93ms ttfb=131ms total=169ms — HTTP/1.1 206, CacheHTTPd v1.0, brak HTTP/2

# T5b: ile KB wystarcza na POPM (plik z oceną, fileid=71496730995):
# 16 KB -> POPM: True; 32 KB: True; 64 KB: True; 128 KB: True => 16 KB wystarcza; 64 KB margines

# T6: getfilelink expires: 18:19:57 → 00:19:58 = ~6 h TTL
```
